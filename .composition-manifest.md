## Deliverables

- `public/website/contact-form.js` — submit backend, loaded as a module on both form pages.
- `public/website/contact-form.config.js` — the shared config global.
- `brand/firebase-rules.json` — the deployed ruleset's source of record.

Both forms (`home.html`, `quick-start.html`) carry `<form id="contact-form">`, the
hidden honeypot, and a `[data-form-status]` live region. Both load the config in an
unconditional top-level `<script>` ahead of the module, per the load rule in
`FEATURE.md` (the glinda regression that lost ~21 days of leads was caused by
breaking exactly that rule).

## Record shape written to `/leads/{pushId}`

| Key | Source | Required by rules |
| --- | --- | --- |
| `email` | form field | yes |
| `message` | form field | yes |
| `page_slug` | derived from the URL, so home and Growth Fix submissions are distinguishable | yes |
| `submitted_at` | `Date.now()` | yes |
| `referrer` | `document.referrer`, when present | no |

The ruleset rejects any key outside this list (`$other: { ".validate": false }`).
Adding a field to either form's markup without redeploying the rules produces the
documented silent failure: HTTP 401 on every write, no CORS error, leads lost.

## Security posture

- `.read` is `false` at the root and on `/leads`. Submissions are not readable from
  the client by anyone. Read them in the Firebase console or via the Admin SDK.
- `/leads/$pushId` accepts creates only (`!data.exists() && newData.exists()`), so a
  submission cannot be overwritten or deleted from the client.
- Field-level validators cap lengths, so the path cannot be used to store bulk data.
- The honeypot is a courtesy filter, not the trust boundary. The rules are.

## Verification, 2026-08-20

Checked against the live database before the forms went public:

| Check | Result |
| --- | --- |
| `GET /leads.json` | Permission denied |
| `GET /comments.json` (no auth) | Permission denied |
| `GET /.json` (root) | Permission denied |
| `POST /leads.json` with an unknown field | Rejected by `$other` |
| `POST /leads.json` missing a required field | Rejected |
| `POST /leads.json`, valid payload | Succeeded |
| Read after a successful write | Still permission denied |
| Submit through the real form on `home.html` | Success state, `contact-form-submitted` fired, form cleared, no console errors |

Two test records are in `/leads` from this verification, both with
`page_slug: "setup-verification"` and a message saying they are safe to delete.
The rules are create-only by design, so they cannot be removed from the client:
delete them in the Firebase console.

## Open items

1. **Fallback email is unconfirmed.** `milos.milosavljevic@nsc.agency` sits in
   `contact-form.config.js`, which is published, so it is scrapable from the page
   source whether or not the fallback ever fires.
2. **Comments rules are inert.** The review widget is not on this site. The
   `/comments` path is ready and correctly denies unauthenticated access, but
   nothing writes to it yet. Adding the widget also needs Google enabled under
   Authentication, otherwise `auth` is always null and the path denies for
   everyone including the allow-listed addresses.
3. **No App Check.** A public write path attracts bots that the honeypot will not
   fully stop. Worth adding if spam appears.
4. **No submission notification.** Leads land in the database silently. Nothing
   emails or pings when one arrives, so the database needs checking, or a Cloud
   Function or Zapier-style hook wiring up.
